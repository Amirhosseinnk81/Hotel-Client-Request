# تحویل یک Stage

این پروژه یک قاعدهٔ ثابت دارد: هیچ Stage ای تمام‌شده حساب نمی‌شود تا وقتی گیت زیر کامل سبز شود و Amirhossein دستی روی مرورگر تأییدش کند. هدف این اسکیل این است که آن روال هر بار یکسان اجرا شود و مغایرت‌های تکرارشوندهٔ این ریپو دوباره از دست نروند.

قواعد کامل پروژه در `CLAUDE.md` ریشهٔ مخزن است؛ این اسکیل جایگزینش نیست، اجرایش می‌کند.

## قدم ۱ — بفهم چه چیزی عوض شده

**این مخزن `.git` ندارد.** فایل‌ها دستی بین دو ماشین ویندوز کپی می‌شوند، پس `git status` و `git diff` اینجا کار نمی‌کنند و نباید به آن‌ها تکیه کنی. دو راه معتبر:

1. فایل‌هایی که خودت در همین نشست ویرایش یا ایجاد کرده‌ای — دقیق‌ترین منبع.
2. اگر مطمئن نیستی، بر اساس زمان تغییر فایل‌ها:

```bash
find . -newermt "YYYY-MM-DD HH:MM" -type f \
  \( -name "*.py" -o -name "*.ts" -o -name "*.tsx" -o -name "*.css" -o -name "*.md" \) \
  -not -path "./node_modules/*" -not -path "./.next/*" -not -path "*/__pycache__/*" \
  -printf "%TY-%Tm-%Td %TH:%TM  %p\n" | sort
```

این فهرست تعیین می‌کند کدام نیمهٔ گیت لازم است. اگر هیچ فایلی زیر `apps/` یا `config/` عوض نشده، اجرای تست بک‌اند اتلاف وقت است — و برعکس.

## قدم ۲ — چک‌های مغارت که تست‌ها نمی‌گیرند

اینها قبل از اجرای تست انجام شوند، چون بعضی‌شان خودشان باعث قرمز شدن تست می‌شوند و زودتر پیدا کردنشان ارزان‌تر است.

**اگر مدلی عوض شده:** `python manage.py makemigrations <app>` را بزن. جا انداختن migration در این پروژه بارها اتفاق افتاده و خطایش موقع اجرا ظاهر می‌شود نه موقع نوشتن.

**اگر API عوض شده** (سریالایزر، ویو، یا مسیر):

```bash
python manage.py spectacular --file Hotel_Client_Request_Platform_API.yaml
```

آن فایل contract معتبر است و هرگز دستی ویرایش نمی‌شود.

**اگر ماشین‌حالت تیکت را دست زده‌ای:** `allowedNextStatuses` در `frontend/src/lib/ticket-labels.ts` باید آینهٔ دقیق `Ticket.ALLOWED_STATUS_TRANSITIONS` در `apps/tickets/models.py` باشد. این دو یک‌بار از هم دررفتند و نتیجه‌اش دکمه‌ای بود که همیشه ۴۰۰ می‌گرفت. تست `ticket-labels.test.ts` الان این را pin می‌کند؛ اگر قرمز شد، سمتِ غلط را درست کن، نه انتظار تست را.

**اگر تعداد تست‌ها عوض شده:** `README.md` و `CLAUDE.md` هر دو عدد تست را می‌نویسند. شمارش واقعی:

```bash
# بک‌اند
cat apps/*/tests.py tests/*.py | grep -c 'def test_'
# فرانت
total=0; for f in $(find frontend/src -name "*.test.*"); do total=$((total + $(grep -c 'it(\|test(' $f))); done; echo $total
```

عدد را در هر دو سند به‌روز کن. این اسناد قبلاً ماه‌ها از کد عقب مانده بودند؛ نگه‌داشتنشان فقط وقتی جواب می‌دهد که هر بار انجام شود.

**اگر فیچر کاربری اضافه شده:** فهرست قابلیت‌ها در `README.md` را هم به‌روز کن.

**اگر تصمیم معماری عوض شده** (پالت، زیرساخت، وابستگی جدید): بخش «تصمیمات معماری» در `README.md` باید دلیلش را ثبت کند. تصمیم ثبت‌نشده همان چیزی است که بعداً باعث می‌شود سند و کد از هم بیفتند.

## قدم ۳ — گیت

به همین ترتیب. **اگر Python یا Node روی این ماشین نصب نیست، وانمود نکن که اجرا شده** — بگو نتوانستی و دستورها را به کاربر بده تا روی ماشین توسعه بزند. گزارش دادن نتیجه‌ای که اجرا نشده بدترین حالت ممکن است، چون تنها چیزی که این گیت می‌فروشد اعتماد است.

**بک‌اند تغییر کرده؟**

```bash
python manage.py test
```

کامل، نه فقط اپ تغییریافته. روی PostgreSQL واقعی، هرگز SQLite. اجرای فقط یک اپ (`python manage.py test apps.tickets`) برای دیباگ میانی خوب است ولی تحویل حساب نمی‌شود — چند بار شکستگی از اپ دیگری درآمده.

**فرانت‌اند تغییر کرده؟** هر سه باید سبز باشند:

```bash
cd frontend
npm run lint
npm run build
npm test
```

`build` را رد نکن. بعضی خطاهای TypeScript فقط آنجا ظاهر می‌شوند، نه در `lint` و نه در تست‌ها — مخصوصاً چیزهایی مثل نبود مرز `Suspense` دور `useSearchParams` که کل صفحه را از prerender می‌اندازد.

اگر `build` خطای عجیبی روی `.next/dev/types/routes.d.ts` داد، اول `.next` را پاک کن و دوباره بزن؛ آن فایل خودکار ساخته می‌شود و گاهی خراب می‌ماند. روی ویندوز:

```bash
cmd /c rmdir /s /q .next
```

## قدم ۴ — جدول تحویل

فقط فایل‌های تغییریافته و جدید، با شماره و مسیر واقعی. کل ریپو را تحویل نده — فایل‌ها دستی کپی می‌شوند و هر سطر اضافه یک فرصت برای اشتباه است.

```markdown
| # | مسیر | تغییر |
|---|---|---|
| ۱ | `frontend/src/lib/room-param.ts` | جدید — پارسر پارامتر اتاق |
| ۲ | `apps/tickets/models.py` | افزودن فیلد X + migration 0010 |
```

ستون «تغییر» یک عبارت کوتاه باشد، نه شرح کامل. اگر migration ساخته شده، شمارهٔ فایلش را همان‌جا بنویس تا موقع کپی جا نماند.

## قدم ۵ — گزارش صادقانه، بعد توقف

گزارش باید این‌ها را روشن بگوید:

- چه چیزی اجرا شد و نتیجه‌اش چه بود. اگر تستی قرمز است، خروجی‌اش را بیاور — نه خلاصه‌اش.
- چه چیزی اجرا **نشد** و چرا (نبود Python/Node، وابستگی نصب‌نشده، هر چیز دیگر).
- اگر وسط کار اشتباهی از خودت گرفتی و درستش کردی، یک خط بگو. لازم نیست عذرخواهی کنی.

بعد **بایست**. Stage بعدی شروع نمی‌شود تا Amirhossein روی مرورگر واقعی تأیید کند. این قاعده از جایی آمده که یک‌بار فیچر تأییدشدهٔ قبلی حین کار روی Stage بعدی از بین رفت.

## چیزهایی که موقع بازبینی کد این پروژه ارزش نگاه کردن دارند

اینها باگ‌هایی هستند که قبلاً واقعاً خورده‌ایم و تست‌ها همیشه نمی‌گیرندشان:

- **`instanceof FormData`** — قبل از ست‌کردن `Content-Type: application/json` در `apiFetch` باید چک شود، وگرنه آپلود چندبخشی بی‌صدا می‌شکند.
- **`read_only_fields = fields`** — اگر سریالایزر قرار است داده هم بپذیرد، ورودی بی‌صدا و بدون خطای validation دور ریخته می‌شود. فقط برای سریالایزرهای صرفاً خواندنی درست است.
- **صفحه‌بندی** — همهٔ لیست‌ها `PageNumberPagination` با `PAGE_SIZE=10` دارند. تستی که فرض کند `response.data` مستقیماً لیست است بی‌صدا فیل می‌شود؛ `response.data["results"]` درست است.
- **`IsAdminRole` در برابر `IsAdminOnly`** — اولی GET را برای هر کاربر لاگین‌شده باز می‌گذارد. هر endpointی که دادهٔ بین‌واحدی می‌دهد باید `IsAdminOnly` باشد.
- **معماری توکن** — refresh فقط در کوکی httpOnly، access فقط در حافظهٔ `client.ts`. هر دست‌کاری در `AuthProvider` یا `client.ts` باید این را حفظ کند.
- **`localhost` نه `127.0.0.1`** — کوکی `SameSite=Lax` این دو را دو سایت متفاوت می‌بیند و ناهماهنگی‌شان نشست را در هر ریلود بی‌صدا می‌شکند.

اگر تغییر فرانت‌اند شامل ظاهر بوده، قواعد بخش «زبان بصری» در `CLAUDE.md` را هم چک کن — مخصوصاً اینکه برنزی (`--accent`) در حالت روشن هرگز رنگ متن یا پرکنندهٔ دکمه نباشد، و تیترها از `.display-*` بیایند نه `font-semibold`.
